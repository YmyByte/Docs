# 优化技术方案
## 有没有使用过 Spark 的列式存储（如 Parquet）或分区剪裁（Partition Pruning）？效果如何？
在某电商用户画像项目中，原始数据以 CSV 格式存储，单表约 5 亿条记录（1.2TB），用户行为分析任务耗时 40 分钟。迁移至 Parquet 后，性能提升显著：

列式存储：将用户行为日志（如点击、加购、下单）从 CSV 转为 Parquet 格式后，查询扫描的数据量减少 85%（从 1.2TB → 180GB）。
压缩与编码：使用 Snappy 压缩（默认）+ 字典编码，存储空间从 1.2TB → 320GB（压缩比 3.75:1），同时提升 IO 效率。
谓词下推：查询 WHERE user_id = '12345' 时，Spark 直接跳过不包含该用户的列组（Row Group），扫描时间从 12 分钟 → 1.5 分钟。

**分区裁剪**：在物流轨迹分析项目中，订单表按 date 字段分区，每日新增约 2000 万条记录。通过分区剪裁，查询性能提升 92%：
按照日期分区
```python
# 创建分区表（按 year/month/day 三级分区）
df.write.partitionBy("year", "month", "day").parquet("hdfs://orders/")

# 目录结构示例
orders/year=2025/month=06/day=23/part-00000.parquet
```
当查询 WHERE year=2025 AND month=06 AND day=23 时，Spark 直接定位到对应分区目录，跳过其他日期的数据：
```python
# 原始全量扫描（未分区）
df = spark.read.parquet("hdfs://orders/")
filtered_df = df.filter("year=2025 AND month=06 AND day=23")

# 优化后（分区剪裁生效）
df_partitioned = spark.read.parquet("hdfs://orders/year=2025/month=06/day=23/")
```

# 数仓模型设计
## 物流数据仓库采用了星型模型还是雪花模型？事实表和维度表是如何设计的？
**星型模型**：
我的业务：实时分析与快速查询：物流订单分析、运输时效监控等需要高频查询的场景。
结构特点：以事实表为中心，维度表直接与事实表关联，形成辐射状结构，无需层级关联。
优势：
结构简单，查询效率高，适合 OLAP 分析。
维度表冗余存储，减少 JOIN 操作，提升查询性能。

**雪花模型**：
我的业务是负责：省→市→区县→网点分层的区域网格划分
结构特点：维度表进一步规范化，拆分为多层级子维度表，形成雪花状结构。
优势：
* 减少数据冗余，提升存储效率。
* 符合第三范式（3NF），便于数据维护和更新。

## 遇到数据倾斜问题时，如何定位瓶颈并优化？请举例说明具体案例。
数据倾斜的本质是数据在计算节点间分布不均，导致部分任务负载过高。定位需结合工具监控与代码分析：
**倾斜 Key 打散处理：双 11 订单聚合优化**
问题场景：电商大促期间，订单数据按promotion_id分组时，promotion_id="618"的订单量占比 35%，导致单个 Task 处理超时。
优化方案：对倾斜 Key 添加随机前缀，先局部聚合再全局聚合

**倾斜 Join 优化：物流订单与网点维度关联**
问题场景：订单表（5 亿条）与网点表（100 万条）按warehouse_idJoin 时，某warehouse_id="WH001"关联次数达 1.8 亿次，导致 OOM。
优化方案：拆分倾斜维度表，采用 “广播小表 + 分桶 Join” 策略
优化效果：Join 任务从频繁失败转为成功执行，耗时从 1.2 小时缩短至 15 分钟，内存占用降低 75%。
