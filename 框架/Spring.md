## Spring的特点
**Spring为什么这么流行**
核心：DI
Spring是**面向接口编程**，依赖倒置，A是一个实体类，B是一个实体类，但A与B之间不是直接依赖， 而是依赖于中间的图像。我这个接口可以注入到所有需要这个接口的程序中，Spring来负责这个接口的实例化，这个好处就在于，可以针对不同场景做一个适配的具体逻辑，它是通过接口隔离，这种上一层的抽象，然后通过IOC，去将我们这个上层的抽象类注入里面去，造成两个客户端不感知，他俩只感知接口，因为接口是稳定的，因为接口没有实现，但实现是不稳定的
**依赖倒置和依赖注入区别：**
依赖倒置核心，是一种设计原则，核心思想就是依赖抽象而非具体实现
依赖注入核心：通过构造函数或注解注入依赖，通过外部注入依赖对象，使代码更加灵活和解耦。
依赖注入是实现依赖倒置原则的一种常见方法。
**特点**：
1、松耦合：Spring通过依赖注入（DI）和面向切面编程（AOP）来解耦对象之间的关系。DI使得对象的依赖关系由容器管理，而AOP则帮助将横切关注点（比如：日志、事务）于业务逻辑分离。
2、简化开发：Spring提供了丰富的工具和库来简化企业应用开发，比如Spring MVC简化了Web开发，Spring Data简化了数据库操作，Spring Security为安全控制提供了全面的支持。
3、容器管理：Spring是一个IOC容器，负责管理对象的生命周期和依赖关系。它提供了BeanFactory和ApplicationContext两种容器实现，支持XML配置、注解配置以及Java配置等多种方式。
4、面向切面编程（AOP）：Spring内置了AOP支持，允许在应用中以声明的方式插入横切关注点（如日志、性能监控、事务控制等），而不需要改变核心业务逻辑代码。

## Springboot和Spring的区别
Springboot的出现主要是为了减少Spring配置的快速开发
* Springboot通过自动配置来减少开发人员的配置上工作
* 内嵌Web服务器（Tomcat），意味着我们可以创建独立的应用程序，不许外部的web服务器

# IOC
控制反转，核心是将对象的创建、依赖关系的维护权，从业务代码中「反转」给 Spring 容器来管理—— 简单说就是我们不再手动 new 对象、手动维护对象间的依赖，一切由 Spring 容器全权负责。

Spring提供了两种不同的类型的容器
* Spring BeanFactory容器:它是最简单的容器，给 DI 提供了基本的支持
* ApplicationContext容器 :ApplicationContext 容器继承自BeanFactory,它包括 BeanFactory 容器的所有功能。

* 依赖注入（DI, Dependency Injection）：DI是IOC的一种实现方式，Spring通过构造器注入、Setter方法注入和字段注入等方式，将对象的依赖注入到对象中。依赖注入可以通过注解（如@Autowired / @Resource）或XML配置实现。
* Bean管理：Spring容器负责管理Bean的生命周期，包括Bean的创建、初始化、销毁等。通过IOC，开发者不再需要手动管理Bean的依赖，容器会自动处理这些依赖关系。
* 松耦合：IOC降低了对象之间的耦合度，使得代码更容易测试和维护。由于对象的创建和依赖关系由容器管理，开发者可以轻松地替换实现或改变配置，而无需修改应用代码

## springbootapplication是怎么实现ioc的
@SpringBootApplication 实现 IOC 的核心是 **「注解组合定规则，启动方法自动化走流程」**：
* 作为复合注解，通过 @ComponetScan、@SpringBootConfiguration、@EnableAutoConfiguration 一站式定义了 Bean 的扫描、配置、自动加载规则，覆盖所有类型 Bean 的收集；
* 配合 SpringApplication.run ()，自动完成 IoC 容器初始化、Bean 定义注册、Bean 实例化 + 依赖注入 + 初始化的全流程，落地 IOC“对象创建 / 依赖维护权反转给容器” 的核心思想；
* 底层基于 Spring 原生 IOC 容器，仅做了自动化封装和约定，简化了原生 Spring 的手动配置，让开发者一行代码就能启动完整的 IoC 容器。 

## 如果业务代码不在启动类子包下，怎么让 IoC 容器扫描到？
@SpringBootApplication 的scanBasePackages属性手动指定扫描包

## 为什么IOC要把Bean交给Spring容器进行管理
把 Bean 交给 Spring 容器管理，是「业务代码和基础设施代码的分离」：我们只需要关注「业务逻辑做什么」，而「对象怎么创建、依赖怎么维护、通用能力怎么加、框架怎么整合」这些通用问题，全部交给 Spring 容器这个来做，最终实现项目的高可维护、高可扩展、高协作性，这也是 Spring 能成为 Java 企业级开发标准框架的核心原因。

## 容器管理的Bean，和手动 new 的对象有什么本质区别？
核心区别是容器管理的 Bean 是「被容器代理 / 管控的实例」，容器持有 Bean 的引用，能干预其生命周期、做动态增强；而手动 new 的对象是「裸实例」，容器无法感知、无法管控，也无法实现依赖注入、AOP 等能力。例如，手动 new 的 Service 对象，其方法不会被容器织入事务切面，因为容器不知道这个对象的存在。

## @Autowired和@Resource区别
来源：@Autowired是Spring框架定义的注解，而@Resource是Java定义的注解。
顺序：@Autowired先按类型查找，如果存在多个Bean再按名称查找；而@Resource则是先按名称查找，如果找不到再按类型查找。
注入：@Autowired支持属性注入、构造方法注入和Setter注入，而@Resource仅支持属性注入和Setter注入，不支持构造方法注入。
提示：在使用IDEA编写依赖注入代码时，如果注入的是Mapper对象，使用@Autowired可能会提示错误，而使用@Resource则不会提示错误。

## Bean生命周期
BeanDefintion获取bean的定义信息，这里面就封装了bean的所有信息（比如：类的全路径、是否是延迟加载、是否是单例）
1、在创建Bean的时候，第一步，调用构造函数实例化bean
2、bean的依赖注入，比如一些set方法的注入、@Autowried自动注入
3、处理Aware接口，如果某一个bean实现了Aware接口，就会重写方法执行
4、初始化前，执行bean的前置处理器，处理@PostConstrut
5、初始化时，处理InitializingBean接口
6、初始化后，执行Bean的后置处理器，主要是对bean进行增强
7、销毁Bean

## **循环依赖问题**
主要是先看我们的业务规范是什么，如果用@Resource的话，基本不会有循环依赖问题，但是如果用构造器注入的话，他可能会有循环依赖。

两个或多个Bean相互依赖，形成一个闭环。例如：
Bean A依赖于Bean B，而Bean B又依赖于Bean A。
这种情况下，Spring容器在实例化时可能会陷入死循环，无法完成Bean的创建。
**解决**：
Spring容器首先会尝试从一级缓存中获取初始化完成的Bean，如果获取不到，就从二级缓存中获取。
如果二级缓存中也没有，Spring会从三级缓存中获取ObjectFactory，并通过它来创建Bean实例，并将实例放入二级缓存。
在创建Bean的过程中，如果遇到循环依赖，Spring可以通过二级缓存中的早期Bean实例继续进行依赖注入，从而打破循环依赖。
**二级缓存**：
二级缓存用来解决 Bean 创建过程中的循环依赖问题，它存储的是**尚未完成属性**注入和初始化的“半成品”Bean 对象；当 Spring容器发现两个或多个 Bean 之间存在循环依赖时，也就是当一个 Bean 创建过程中需要引用另一个正在创建的 Bean，Spring 将创建需要的这些未完全初始化的对象提前暴露在二级缓存中，以便其他 Bean 进行引用，确保它们之间的依赖能够被满足。
**三级缓存**：
三级缓存中存储的是 ObjectFactory<?> 类型的**代理工厂对象**，主要用于处理**存在 AOP 时的循环依赖**问题；每个 Bean 都对应一个 ObjectFactory 对象，通过调用该对象的 getObject 方法，可以**获取到早期暴露出去的 Bean**；在该 Bean 要被其他 Bean 引用时，Spring 就会用工厂对象**创建出该 Bean 的实例对象**，最终当该 Bean 完成构造的所有步骤后就会将该 Bean 放入到一级缓存中。

## 为什么不能是四级或二级缓存
一级缓存：存放完全初始化完成的 Bean。
二级缓存：存放仅完成构造但未初始化的 Bean。
三级缓存：存放 Bean 的工厂，可在需要时动态创建 Bean，支持 AOP 代理。
四级缓存并没有额外的作用，徒增复杂性

如果只有二级缓存，无法对 Bean 进行代理增强，会导致：AOP 失效（无法代理 Bean）；获取的可能是原始对象，而不是代理对象，造成不一致问题。

## BeanDefinition的作用
首先beanDefinition中含有对于bean的一些基础元信息的描述，通过这个步骤还可以控制bean的生命周期。作为spring 容器bean的注册表，用beanDefinition来保存bean的配置信息并通过他来实例化管理bean。

## Bean的懒加载
指的是bean在容器启动的时候不立刻实例化bean而是在第一次创建的时候才实例化。

## Bean的作用域
1.singleton，默认的单例作用域，整个spring容器中只有一个bean实例，所有对该bean的请求都返回同一个实例。
2.prototype，原型作用域，每次请求都创建一个新的bean实例，适合有状态的bean或者需要不同实例的场景。
3.session，在web应用中有效，每个http会话会创建一个实例，适用于需要在整个会话中共享数据的场景。
4.application，也是会话中有效，适用于全局共享数据的场景
5.websocket，每个websocket会话创建一个实例
6.request：每个http请求创建一个bean实例。

## 多线程并发环境下Singleton作用域可能会出现的问题：
在多线程并发环境下，使用singleton作用域的Bean可能会导致**线程安全问题**。由于所有线程共享同一个Bean实例，如果该Bean是有状态的（即持有一些可变的成员变量），不同线程同时修改这些变量可能会导致数据不一致、竞态条件等问题。

# AOP
应用：基于 AOP 实现统一的日志管理,全局异常信息处理,自定义枚举类统一返回格式,使用 Knife4j 进行接口管理。

AOP一种面向切面编程的思想，主要就是在不修改现有业务逻辑代码的情况下，动态的添加或修改程序的执行逻辑。什么是切面，简单来说切面：编写公共逻辑代码的那个类，通过@Aspect注解的类实现

## 原理
Spring AOP的原理主要是基于代理模式，如果我们为Spring的某个bean配置了切面，那么Spring在创建这个bean的时候，实际上**创建的是这个bean的一个代理对象**，我们后续对bean中方法的调用，实际上调用的是**代理类重写的代理方法**。通过JDK动态代理(**默认**)和CGLIB动态代理实现对方法调用的拦截，在方法执行的前后或过程中插入切面逻辑。通过配置切点和通知，Spring AOP可以灵活地将横切关注点（如事务管理、日志记录等）应用到目标对象的特定方法上，使得核心业务逻辑与横切关注点的代码分离，提升代码的可维护性和复用性。

## JDK 动态代理和 CGLIB 动态代理比较
**区别**：
JDK 动态代理基于接口，CGLIB 动态代理基于类。因为 JDK 动态代理生成的代理类需要继承java.lang.reflect.Proxy，所以，只能基于接口；CGLIB 动态代理是根据类创建此类的子类，所以，此类不能被 final 修饰
JDK 和 CGLIB 动态代理都是在运行期生成字节码。而 JDK 是直接写 Class 字节码；而 CGLIB 使用 ASM 框架写 Class 字节码（不鼓励直接使用ASM，因为它要求你必须对 JVM 内部结构包括 class 文件的格式和指令集都很熟悉）
JDK 通过反射调用方法，CGLIB 通过 FastClass 机制直接调用方法。所以，CGLIB 执行的效率较高
JDK 动态代理是利用反射机制生成一个实现代理接口的类（这个类看不见摸不着，在 jvm 内存中有这个类），在调用具体方法前调用 InvokeHandler来处理。核心是实现 InvocationHandler接口，使用 invoke()方法进行面向切面的处理，调用相应的通知；CGLIB 动态代理是利用 asm 开源包，对代理对象类的 class 文件加载进来，通过修改其字节码生成子类来处理。核心是实现 MethodInterceptor 接口，使用 intercept() 方法进行面向切面的处理，调用相应的通知。
**优缺点**
**劣势**：
JDK：JDK的动态代理机制只能代理实现了接口的类，而不能实现接口的类就不能实现JDK的动态代理
CGLIB：CGLIB 的原理是对指定的目标类生成一个子类，并覆盖其中方法实现增强，但因为采用的是继承，所以不能对 final 修饰的类进行代理
**优势**：
JDK：最小化依赖关系，减少依赖意味着简化开发和维护，JDK本身的支持，可能比 cglib 更加可靠
JDK：平滑进行JDK版本升级，而字节码类库通常需要进行更新以保证在新版Java 上能够使用。代码实现简单
CGLIB：从某种角度看，限定调用者实现接口是有些侵入性的实践，类似cglib动态代理就没有这种限制。只操作我们关心的类，而不必为其他相关类增加工作量。另外高性能。

## 注解的理解
注解通俗点理解就是代码中的特殊标记，这些标记可以在编译、类加载、运行时被读取，并执行相对应的处理。注解在日常开发也是非常常见的比如：使用spring框架中的@Controller、@service或者像model层使用lombok注解@data等等。除了框架实现的注解java原生的也有@Overried@FunctionalInterface等基本注解，不过java原生的基本注解大多数用于标记和检查。
	原生java出了提供基本注解外，还有一种叫做元Annotation，所谓的元Annotation注解就是用来修饰注解的，常用的有@Retetion和@Target。@Retetion注解可以简单理解为设置注解的生命周期，而@Target表示这个注解可以修饰什么地方（比如方法、还是成员变量还是包等等）

## 自己是否写过注解
写过的，首先讲一下背景：在奥坦途车连网系统中，需要对一些接口比如车辆上线、碰撞触发等接口需要在方法执行前后记录日志。如果需要在原来业务代码里面插入就会比较混乱跟原有的业务逻辑。
	这种基础的日志信息，我这边是通过AOP切面的方式去处理掉的，而再用注解这个载体配置相关的信息，配合AOP的解析就会相对优雅一点。
	写自定义的注解，首先考虑我们是在什么时候解析这个注解。这就需要用到@Retetion注解，这个注解会修饰我们自定义注解的生命周期，@Retetion注解传入的是RetetionPolicy枚举，枚举三个常量，分别是source,class,和runtime。一般来说只要自定义的注解中@Retention注解设置为SOURCE和Class这两个级别就需要继承并实现，因为这两个级别等加载到jvm的时候注解就被抹除了这里也引申出lombok的实现原理。
一般来说我们自定义的注解都是runtime级别的，因为大多数情况我们是根据运行时环境去做一些处理，我们在开发的过程种写自定义注解需要搭配反射来使用（获取注解）。所以我当时就用了自定义注解，在Spring AOP的逻辑处理中，判断是否带有自定义注解，如果有则将对应的日志逻辑写到方法的前后，这样只需要在方法上加上我的注解就能实现这个效果。
补充案例：
切点定义成了一个注解，然后又把切点和Around绑定，也就是这个标注了这个注解会走到这个环绕AOP.
为什么要用环绕不用前置，因为前置只能判断有没有权限，不能告知用户没有权限。因为他不能控制返回。
为什么在没有权限要返回自定义异常GlobalException，因为这里return出去的必须和被增强的Controller方法返回的一致。所以这里是定义了一个该自定义异常的Advice，里边把返回包装成了和Controller方法返回的内容也就是同一的ResponseResult对象。

## 为什么需要AOP结合自定义注解一起使用？直接使用aop行不行？
整合自定义注解与Spring AOP结合使用有以下几点好处：
* 代码解耦：通过使用自定义注解，可以将横切关注点（cross-cutting concerns）与业务逻辑进行解耦。将横切关注点的逻辑从业务代码中抽离出来，以注解的形式标记需要被切面处理的方法或类，提高了代码的可读性和可维护性。
* 重用性和灵活性：通过自定义注解，可以在不同的方法或类上进行标记，使得切面逻辑可以在多个地方进行重用。同时，通过AOP的机制，可以动态地在运行时将切面逻辑织入到被标记的方法或类中，提供了更大的灵活性。
* 横切关注点的集中管理：通过使用自定义注解，可以将不同的横切关注点集中管理。在切面类中，可以定义多个切面逻辑，并使用不同的注解来匹配不同的方法或类。这样，可以将相同的横切关注点逻辑应用于多个地方，实现了逻辑的复用和集中管理。
* 提高开发效率：通过使用自定义注解和Spring AOP，可以减少重复的代码和冗余的逻辑。横切关注点的逻辑只需要在切面中定义一次，然后通过注解的方式应用于多个方法或类中。这样可以提高开发效率，并减少代码的维护成本。

# ORM
核心是通过抽象与映射弥合面向对象编程与关系型数据库的语义鸿沟，让我们以 “对象思维” 处理数据，同时通过框架内部的优化机制（如查询缓存、事务管理）平衡开发效率与性能。
**优势**
开发效率提升：减少 SQL 编写，专注业务逻辑，代码更易读维护。
跨数据库兼容：通过 ORM 层屏蔽数据库差异，便于项目迁移（如从 MySQL 切换到 PostgreSQL）。
安全性增强：自动处理 SQL 注入问题（如参数化查询），避免手动拼接 SQL 的风险。
**局限性**
性能损耗：对象与数据的转换、复杂查询的自动优化可能导致性能开销（如 “N+1 查询” 问题）。
灵活性不足：复杂业务场景下（如多表联合统计、自定义 SQL 函数），ORM 可能无法完全替代原生 SQL。

# Springboot启动流程
1、spring启动的时候首先会加载应用程序的配置，包含：读取xml配置文件以及扫描带有注解的类比如@Component等，这些配置文件定义了应用程序中各种bean以及其依赖方式，在springboot中由springapplication.run方法触发
2、创建应用程序上下文即spring容器，负责管理bean的生命周期并在需要的时候提供一个依赖注入。
3、beanDefinition的加载和解析，解析出每个bean的定义信息，生成beanDefinition对象，并将其注册到容器中，包含了bean的的类名、作用域、初始化方法等信息。
4、实例化bean，spring通过反射的机制创建bean实例。
5、依赖注入，依赖注入可以通过构造函数注入、setter方法注入，根据beanDefinition中的元信息以及应用程序中定义的依赖关系，将需要的依赖注入到bean中。
6、beanPostProcessor的执行，这个步骤允许对bean的进一步处理例如：修改bean属性或者实现aop等功能，这也是spring提供的一个扩展点，用户可以在bean初始化的前后添加自定义逻辑。
7、初始化回调和生命周期方法。
8、启动事件的发布。Spring容器此时会发布一个contestrefershedEvent，通知所有注册的监听器应用上下文已经完全初始化并可使用。这个时候应用已经可以接受和处理请求了。

## SpringBoot 打成的jar和普通的jar有什么区别
Spring Boot 项目最终打包成的 jar 是可执行 jar ，这种 jar 可以直接通过 java -jar xxx.jar 命令来运行，这种 jar 不可以作为普通的 jar 被其他项目依赖，即使依赖了也无法使用其中的类。
SpringBoot 的 jar 无法被其他项目依赖，主要还是他和普通 jar 的结构不同。普通的 jar 包，解压后直接就是包名，包里就是我们的代码，而 Spring Boot 打包成的可执行 jar 解压后，在 \BOOT-INF\classes 目录下才是我们的代码，因此无法被直接引用。如果非要引用，可以在 pom.xml 文件中增加配置，将 Spring Boot 项目打包成两个 jar ，一个可执行，一个可引用。
