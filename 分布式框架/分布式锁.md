# 分布式锁

## **CAP**
* 一致性（C）：在分布式系统中的所有数据备份，在同一时刻是否为同样的值（等同于所有节点访问同一份最新的数据副本）
* 可用性（A）：在集群中一部分节点故障后，集群整体是否还能响应客户端的读写请求
* 分区容忍性（P）：系统如果不能在有限的时间内达成数据一致性，就意味着发生了分区情况，必须就当前操作在C和A之间做出选择

三者不可同时兼得。

## Redis + Lua脚本实现分布式锁
分布式锁是在分布式并发场景下，控制某个资源在同一时刻只能被一个应用所使用。
Redis的`SET NX`可以实现`key`不存在才插入，所以可以用它来实现分布式锁，如果`key`不存在则显示插入成功，表示加锁成功了；如果`key`存在，则显示插入失败，表示加锁失败。
加锁的时候，我们一般会添加几个条件，包括锁的过期时间，以避免客户端拿到锁后发生异常，导致锁一致无法释放；同时为每个客户端设置一个唯一值，用于标识客户端，来避免释放锁的时候，出现误释放的操作。
```sh
SET lock_key unique_value NX PX 10000
````
* unique_value就是客户端生成的唯一标识，用来区分不同客户端的锁操作。
* NX代表只在lock_key不存在时，才对lock_key进行设置操作
* PX 10000 表示设置lock_key的过期时间为10s，为了避免客户端发生异常无法释放。

对于解锁操作，为了保证执行删除操作的客户端就是加锁的客户端，这种操作原子性，采用`Lua`脚本实现锁的原子性解锁。
```lua
// 释放锁时，先比较unique_value是否相等，避免锁的误删除
if (redis.call("get", KEY[1] == ARGV[1]) then return redis.call("del", KEY[1])
else 
 return 0
end
```

## Zookeeper实现分布式锁
利于ZK的临时顺序节点和watcher机制，实现分布式锁
> watcher：当创建一个节点时，可以注册一个该节点的监听器，当节点状态发生变化时，watcher出发时，ZK会想客户端发送一条通知，watch只能被触发一次。

Zookeeper实现的分布式锁是强一致的，**因为它底层的ZAB协议（原子广播协议）天然满足CP**，但是这也意味着性能下降，因为说性能和一致性是一个天平，不能同时满足。如果我们项目中没有强以来ZK使用Redis就好，因为大部分项目都引用了Redis，没必要在对此引入一个新组件还要去后期维护，如果业务场景对于Redis异步方式同步数据造成所丢失无法忍受，在业务层处理就好了。
